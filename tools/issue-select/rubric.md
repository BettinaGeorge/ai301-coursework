# Rubric: is this a good first issue?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| commits-alive | The "last 5 default-branch commits" list under Repo facts (live: the commit history linked from the repo front page), reading each commit's author and date. | At least 2 of the last 5 default-branch commits are dated within 90 days of the bundle's capture date AND are attributable to a human. A commit from an account whose username ends in `[bot]` is attributable to a human only when it merges a pull request opened by a named human; a bot's own automated maintenance commit (for example `pre-commit autoupdate`) is not human activity even when it carries a PR number. In live mode, measure against today rather than a capture date. | required |
| responds-to-issues | The "maintainer first-response sample" under Repo facts, plus the `author_association` field on each comment in this issue's own thread (live: Owner / Member / Collaborator badges on recently-updated issues). | At least one first response from an Owner, Member, or Collaborator arrived within 45 days in the response sample. When reading the sample, ignore rows for issues that had been open fewer than 30 days at the capture date: a young issue without a reply is not evidence of neglect. If every row is ignored on that basis, or the sample is absent or empty, this check passes instead when a maintainer-badged account has commented within 45 days anywhere the evidence reaches — this issue's own thread, or any other issue or pull request thread in the same repository. That second fallback exists because a repository younger than the response window has no old issues to sample, and a young repository is not a neglected one. Grade `unclear` only when no maintainer-badged comment can be found in any available source. | required |
| repo-in-use | The `archived:` flag and `stars` on the repo line, the "latest release" line, and "last push to any branch" under Repo facts (live: the archived banner, the Releases sidebar box, and the newest commit date). | The repo is not archived, AND either its latest release is dated within 365 days of the capture date OR the default branch was pushed to within 90 days of the capture date. Either one is sufficient — a project that ships continuously without cutting releases is in use, and so is a stable project that released this year. An archived repo always fails, whatever else is recent. | required |
| scope-bounded | The issue body and its full comment thread. | The issue asks for work a newcomer could finish in a single pull request and then be done. It fails when any of these is true: it is an umbrella, tracking, or self-described "mega" issue whose sub-items are meant to be split into separate issues or pull requests; it asks for open-ended repeating work with no defined endpoint (for example "add type annotations across the codebase", which is never finished); the thread shows the design still being debated with no maintainer having settled it; a maintainer states the fix touches core internals (for example "this needs changes to the parser"); it is a feature request with no spec on which no maintainer has yet agreed the feature should exist, so a product decision is still open; or it is a pure usage or support question rather than a request for a change. Two things that do NOT fail this check: an issue that names several specific files to change, or lists several concrete sub-tasks that together form ONE deliverable finishable in a single pull request — a long explicit spec is the most bounded kind of issue, not the least; and a terse bug report, a missing reproduction, or a bare acceptance-criteria checklist. Grade the size of the work being asked for, not the length or polish of the write-up. | required |
| unclaimed | The `assignees:` and `linked PRs:` lines (with each PR's state) under Repo facts, plus every claim comment in the thread and its date (live: the Assignees box, the Development box, and the thread — when the sidebar and the thread disagree, believe the thread). | There is no assignee, no linked PR in the open state, and no claim comment from a non-author ("I'll take this", "can I work on this", "working on this") dated within 90 days of the capture date. A linked PR that is closed and unmerged is an abandoned attempt and does NOT fail this check; neither does a claim comment older than 90 days, whether or not anyone replied to it. | required |
| policy-allows-ai | The "contribution policy" line under Repo facts (live: `CONTRIBUTING.md` in the repo root or `.github/`, any contributor docs it links to, a dedicated `AI_POLICY.md` / `AI_USAGE_POLICY.md`, and the PR template). | The stated policy does not ban AI-generated or AI-assisted contributions. A policy that is silent on AI passes. A policy that sets conditions — disclose AI use, personally understand the change, test it, human-review the output — passes, because conditions are terms to follow, not bans. Only an outright ban ("we do not accept AI-generated code") fails. An `AGENTS.md` file is a positive signal, not a restriction. | required |
| labeled-friendly | The issue's labels. | The issue carries a `good first issue`, `good-first-issue`, `beginner`, or `help wanted` label applied by the project. | preferred |
| maintainer-in-thread | The `author_association` on comments in this issue's own thread. | An Owner, Member, or Collaborator has commented on this issue at least once. | preferred |
| spec-included | The issue body. | The body names the expected behaviour, the file or command to change, or an acceptance-criteria list, so the work can start without asking a clarifying question first. | preferred |

## Verdict rule

Accept the issue only if every `required` check grades `pass`. Any single
`required` check graded `fail` rejects it, and a `required` check graded
`unclear` counts as a fail — a first issue whose evidence I cannot verify is
not a first issue I should take.

`preferred` checks never change the verdict. They are reported with their
grades either way, and on an accepted issue they are what ranks it against
the other accepted candidates: an accepted issue passing all three preferred
checks outranks an accepted issue passing none. An `unclear` on a preferred
check is reported and otherwise ignored.
